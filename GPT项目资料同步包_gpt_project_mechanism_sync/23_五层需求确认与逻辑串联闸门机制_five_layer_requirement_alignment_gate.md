# 六层需求确认与实现设计闸门机制

## 文件定位

本文件规定 `video_capability_lab` 项目在遇到问题、需求不清楚、需要修改、机制冲突、执行方式变化、判断标准变化、失败反馈路由变化，或 GPT 准备下发 Codex 执行单前，如何先把需求和实现方案确认清楚，再决定是否下发 Codex。

本机制从原“五层需求确认与逻辑串联闸门”升级为“六层需求确认与实现设计闸门”，新增 `实现设计层`。

本机制只承载 GPT / Codex 配合机制，不承载项目事实，不修改项目审美来源，不迁移旧项目业务事实，不验证 Remotion、HyperFrames、BGM、API、render 或正片候选能力。

文件路径暂时保持 `23_五层需求确认与逻辑串联闸门机制_five_layer_requirement_alignment_gate.md`，用于保持同步脚本、GPT Project 上传包和既有读取链路稳定；语义以本文标题和内容为准。

## 触发条件

命中以下任一情况时触发：

1. 项目执行结果不符合用户预期。
2. 用户反馈“不对 / 怪怪的 / 差点意思 / 冲突了 / 没按之前的来 / 为什么这样做”。
3. 用户需求不清楚，继续执行会让 Codex 猜。
4. 需要修改现有视频、视觉、卡片、动效、声音、剪辑、BGM、调色、自动化、脚本、工具路线、机制、流程、判断标准或失败反馈路由。
5. 执行方式发生变化，例如从 `Remotion 自绘` 改为 `API 出图 + Codex 后处理 + Remotion 贴入`。
6. 新需求可能和已有参考视频迁移规则、视觉语言、锚点机制、资产管线、BGM、调色、正片流程产生冲突。
7. GPT 准备下发 Codex，但目标、机制、实现设计、流程、判断标准、反馈层任一项不清楚。
8. Codex 执行单缺少首选实现路线、备用路线、能力边界、probe 要求、fallback 或 blocked 条件。

## 不触发条件

以下情况默认不触发，避免项目被流程拖慢：

1. 正常执行，目标清楚、边界清楚、实现设计清楚、流程清楚。
2. 正常做视频，已进入已确认流程，且没有异常反馈。
3. 简单事实问答。
4. 单点小修改，且不会影响项目机制、实现路线、判断标准或失败路由。
5. 用户明确说“这轮只执行，不要重新确认”，且不存在明显冲突、风险、需求不清或实现设计缺失。

## 默认动作

触发后，GPT 不能直接下发 Codex，必须先输出“六层需求确认版”。

六层需求确认版必须包含：

### 1. 目标层

说明这次真正要服务什么结果。

必须回答：

- 本轮真正要达成什么。
- 这是项目总目标、阶段目标，还是本轮最小执行目标。
- 本轮不解决什么，避免目标扩大。
- 如果当前目标和旧目标冲突，先提醒用户确认。

### 2. 机制层

说明什么情况触发、什么情况禁止、什么情况降级。

必须回答：

- 触发条件是什么。
- 禁止条件是什么。
- 降级条件是什么。
- 哪些能力仍是 `待验证`。
- 哪些前提不成立时必须 `blocked`。

### 3. 实现设计层

说明 GPT 下发 Codex 前已经锁定的执行方案、能力边界和失败处理。

必须回答：

- 首选实现路线是什么。
- 备用路线是什么。
- Codex 当前已验证能力是什么。
- 待验证能力是什么。
- 是否必须先做 `component_probe`、`technical_sample` 或 `toolchain_completion`。
- 是否允许 `render`、外部 API、安装依赖或写脚本。
- 哪些部分 GPT 必须先判断。
- 哪些部分 Codex 可以自主补全。
- 哪些部分 Codex 禁止猜。
- 需要哪些输入字段、输出字段、执行入口和验证命令。
- fallback 怎么走。
- blocked 条件是什么。
- 缺实现设计层时必须输出 `blocked_need_implementation_design_layer`。

实现设计层必须明确 route，例如 `Remotion`、`FFmpeg`、`API`、脚本、人工素材选择或组合方案。未验证能力必须先 probe，或明确标为 `待验证`；不能让 Codex 到执行阶段再决定核心技术路线。

### 4. 流程层

说明确认后按什么顺序执行。

必须回答：

- 确认后按什么顺序执行。
- 是否需要多路线候选。
- 是否需要最小片段测试。
- 是否需要用户回审。
- 哪些交给 GPT 判断。
- 哪些交给 Codex 执行。
- 哪些需要用户确认。

Execution steps 只承载执行步骤，不承担实现设计职责；实现路线必须提前在实现设计层锁定。

### 5. 判断标准层

说明什么算通过，什么算失败。

必须回答：

- 技术通过标准。
- 内容通过标准。
- 审美通过标准。
- 人感通过标准。
- 失败标准。
- 哪些不能因为“技术完成”就写成“内容通过”。

技术完成不能冒充内容通过；链路跑通不能冒充 capability 已验证。

### 6. 反馈层

说明失败后回到哪一层。

必须回答：

- 方向错，回目标层或机制层。
- 实现路线错，回实现设计层。
- 执行粗糙，回流程层。
- 审美不清，补 reference。
- 素材不支持，回素材层。
- API、权限、余额、依赖失败，进入 `blocked`，不继续硬做。
- capability 未 probe，不得写 `已验证`。

## 逻辑串联要求

GPT 必须检查六层之间是否串得上。

至少检查：

1. 目标层和机制层是否一致。
2. 机制层和实现设计层是否一致。
3. 实现设计层是否真的能支撑流程层执行。
4. 流程层是否真的能产出判断标准层要验收的结果。
5. 判断标准层是否覆盖技术、内容、审美、人感和风险。
6. 反馈层是否能把失败送回正确位置，而不是统一让 Codex 重试。
7. 如果本轮改变了执行方式，必须检查旧机制是否需要同步调整。
8. 如果本轮能力仍是 `待验证`，不得把实现设计写成能力已确认。

## 冲突提醒要求

当本轮需求和已有机制、旧执行方式、旧判断标准、旧失败路由存在冲突时，GPT 必须主动提醒用户。

常见冲突包括：

1. 审美来源不变，但执行方式变了。
   - 例如：仍然使用对标视频迁移来的视觉语言，但执行方式从 `Remotion 自绘` 改成 `API 出图 + Codex 后处理 + Remotion 贴入`。
   - GPT 必须提醒：审美标准不能重写，但执行管线、锚点绑定、资产验收和失败路由需要同步调整。

2. 技术链路完成，但内容目标未完成。
   - 例如：生成了 alpha 图，Remotion 也消费了，但图不是按原需求生成，或位置没有按真实锚点绑定。
   - GPT 必须提醒：这只能算链路部分成立，不能算视频效果成立。

3. 数量达标，但语义不达标。
   - 例如：要求 5 张以上图，Codex 用补位资产凑够数量。
   - GPT 必须提醒：补位资产只能测试链路，不能算自动识别能力通过。

4. 旧流程和新流程职责混乱。
   - 例如：以前 Remotion 负责画贴纸，现在 API 负责生成贴纸，Codex 负责后处理和锚点，Remotion 只负责贴入渲染。
   - GPT 必须提醒：不能再用旧的 Remotion 自绘验收标准覆盖新管线。

5. reference 缺失或审美不清。
   - GPT 必须提醒先补 reference，不能让 Codex 猜审美。

6. 实现设计缺失。
   - GPT 必须提醒缺首选路线、fallback、能力边界、probe 或 blocked 条件；不得用“更长 prompt”替代实现设计。

## 默认输出格式

每次触发本机制时，GPT 先输出：

1. 我理解的目标层
2. 机制层
3. 实现设计层
4. 流程层
5. 判断标准层
6. 反馈层
7. 可能冲突点
8. 默认假设
9. 待确认位
10. 确认后再下发 Codex

在用户确认前，不输出最终 Codex prompt。若用户明确授权按默认假设执行，GPT 也必须把实现设计层写入执行单。

## Codex 执行单最低实现设计字段

Codex 执行单涉及视频、视觉、卡片、动效、声音、剪辑、BGM、调色、自动化、脚本、工具路线、机制修改、正片候选或 Codex 执行时，必须包含：

```yaml
implementation_design:
  primary_route:
  fallback_route:
  capability_status:
    confirmed:
    partially_true:
    pending_validation:
  probe_required:
  allowed_codex_autonomy:
  forbidden_codex_guessing:
  required_inputs:
  required_outputs:
  execution_entrypoints:
  validation_commands:
  blocked_if_missing:
```

缺少上述字段，或字段无法说明首选路线、fallback、能力边界、probe 要求和 blocked 条件时，Codex 必须输出：

```text
blocked_need_implementation_design_layer
```

## 示例：视觉增强需求

以下只是结构示例，不是当前项目事实，不得迁移为 `video_capability_lab` 的固定业务目标。

目标层：
让视频画面更有吸引力、更有空间层次、更能展示核心对象，同时不破坏当前视频目标。

机制层：
当画面太平、缺少层次、主体展示弱、节奏单一时，触发视觉增强机制。
当素材质量差、主体被遮挡、reference 缺失、口型未对齐或关键前提不成立时，禁止直接进入最终执行。
当重特效成本过高或不稳定时，降级为轻量视觉增强。

实现设计层：
首选路线为先做 2-4 秒视觉增强 `component_probe`，再决定是否扩展；fallback 为降低到轻量遮罩、基础转场或静态构图优化。
已确认能力只限已有仓库事实和验证结果；未 probe 的 Remotion 特效、外部 API、BGM 卡点或自动调色一律 `待验证`。
Codex 可以补字段、脚本、检查和报告；不得猜审美路线、核心技术路线或把 render 成功写成内容通过。

流程层：
先诊断片段问题，再生成 3 套视觉路线，再选主路线，再做最小片段测试，再回审，通过后扩展整条视频。

判断标准层：
通过标准：主体更突出、画面更有层次、信息更清楚、特效不抢戏、节奏更顺。
失败标准：遮挡主体、字幕不可读、假 3D 感明显、节奏被打碎、特效比主体更抢戏。

反馈层：
如果效果方向错，回机制层。
如果实现路线错，回实现设计层。
如果执行粗糙，回流程层。
如果审美不清，补 reference。
如果素材不支持，回素材层。
如果这条视频目标本身不适合，回目标层重判。

## 停止线

- 如果缺实现设计层，不得下发 Codex prompt。
- 如果 Codex 收到的执行单缺实现路线、能力边界、fallback 或 blocked 条件，必须 `blocked_need_implementation_design_layer`。
- 不能用“更长 prompt”代替实现设计。
- 不能让 Codex 边执行边决定核心技术路线。
- 如果六层需求没有确认清楚，不能下发 Codex。
- 如果缺的是审美、reference、素材、目标或执行方式冲突，不能用更长 prompt 代替确认。
- 如果当前需求只是正常执行或正常做视频，且目标清楚、实现设计清楚、流程清楚、没有异常反馈，不触发本机制。

## 失败判定

出现以下情况视为执行失败：

1. 用户遇到问题或需求不清，GPT 直接给 Codex prompt，没有先按六层确认。
2. 六层之间逻辑不连贯，GPT 没有提醒。
3. 只有目标和流程，没有实现设计。
4. Codex 自行决定核心实现路线。
5. 没有 probe 就直接正片。
6. 把执行链路跑通写成能力成立。
7. 执行方式改变后，GPT 没有提醒旧机制和新流程冲突。
8. Codex 用补位、降级、替代路线完成数量目标，GPT 没有区分真实达成和链路测试。
9. 技术完成被写成内容通过。
10. 用户反馈“不对 / 冲突 / 不是这个意思”后，GPT 仍继续补 prompt，而不是回到六层需求确认。

## 一句话执行口径

正常执行不加流程；一旦遇到问题、需求不清、机制冲突或 Codex 下发前实现方案不清，先用六层确认把目标、机制、实现设计、流程、判断标准和反馈路由串起来，再决定是否下发 Codex。
