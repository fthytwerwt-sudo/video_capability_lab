# 路线重判与失败后改线机制

## 文件定位

本文件规定当能力 probe、脚本、验证、push 或执行路线失败时，如何判断失败层级并改线。

## 触发条件

- 同一路线连续失败，且无新证据改善。
- 验证脚本、unittest、diff check、push 或 remote HEAD readback 失败。
- 继续推进会变成生成视频、调用 API、迁移旧业务事实或扩大任务边界。
- capability 仍未验证，却被写成可用。

## 默认动作

1. 先判断失败发生在执行层、参数层、机制层、路线层或权限层。
2. 执行层失败优先修复并重跑验证。
3. 权限或远端失败必须写 `blocked_push_failed` 或对应 blocker。
4. 路线层失败时停止重复原动作，重新列出保留、降级、放弃、改走什么。
5. 改线后同步当前任务、检查标准和最新摘要，防止旧路线残留。

## 例外 / 停止线

- 偶发命令错误尚未形成路线失败时，可以修复后重跑。
- 用户明确要求只做一次只读判断时，不进入改线落库。
- 改线不能被写成 capability 已验证或项目成功。

## 失败判定

- 已有验证失败却继续提交。
- push 失败仍写 `completed`。
- route change 后入口文件仍保留旧路线默认优先权。

## 一句话执行口径

失败先分层，能修就修，不能修就重判；push 和远端验证失败时绝不写完成。
